| 4 | 2026-09-07 | Approval gate | The seven destructive tools (`nova_shard_archive`, `nova_shard_forget`, `nova_shard_consolidate`, `nidhogg_ingest`, `nidhogg_scan`, `nova_evolve`, `nova_forgemaster_sprint`) ask for approval through MCP elicitation. ## Resolved

| # | Date | Component | Description | Fix |
|---|------|-----------|-------------|-----|
| 2 | 2026-04-02 | NOVA `nova_shard_create` | Shard creation timed out. Post-write `enrich_shard` embedding hook blocked the async event loop on cold model load. | Moved all three `enrich_shard` call sites (`nova_shard_create`, `nova_shard_update`, `nova_shard_merge`) to run via `asyncio.get_event_loop().run_in_executor(None, ...)`. |
| 3 | 2026-03-26 | NOVA MCP startup | `ModuleNotFoundError: No module named 'filelock'` — server failed to start after a code change introduced a new dependency. | Ran `pip install -r mcp/requirements.txt`. The project targets Python 3.11–3.12; the image and both CI jobs pin 3.11. |
| 5 | 2026-09-07 | Dependency pin | **Every fresh install and `docker build` produced a server that could not start.** `mcp/requirements.txt` and `pyproject.toml` pinned `mcp[cli]>=1.0.0` with no upper bound, which resolved to SDK 2.1.1; v2 removed `mcp.server.fastmcp`, which `nova_server.py` imported. The image built clean and failed only at container start, because the build never imports the server. CI missed it because `requirements-dev.txt` pinned `mcp[cli]==1.2.0`, which won the resolution — so tests ran against a 2024-11-05 protocol while production installed a broken 2026 one. | Bounded the pin, then ported to SDK v2 (`mcp[cli]>=2,<3`, spec 2026-07-28). Added a `runtime-install` CI job that installs `mcp/requirements.txt` alone, asserts the resolved SDK major, and imports the server — the check that would have caught it. |
| 6 | 2026-09-07 | `nova_calibrate_routing` | Raised `AttributeError` on every call. A stray blank line in `schemas.py` put `include_forgemaster` and `include_replay_divergence` on `HuginnCandidatesInput` instead of `CalibrateRoutingInput`, so the runner read fields its params model did not have. `nova_huginn_candidates` meanwhile advertised two booleans it never read. | Moved both fields to the model whose handler reads them. Added `tests/test_calibrate.py`. |
| 7 | 2026-09-07 | MCP wire protocol | Failed tool calls were indistinguishable from successes. Every handler returns a JSON string, so the SDK reported `isError: false` for all of them — a missing shard, a permission denial and a successful read looked identical to any client that does not parse NOVA's payload shape. | Server middleware (`mcp/result_middleware.py`) sets `isError` on any result whose payload reports a failure, for all 41 tools at once. |
| 8 | 2026-09-07 | Capability gate | Destructive tools ran without asking. `ServerContext` bootstraps `active_skill` to `OPERATOR_DIRECT` (TESTED + wildcard capability) and `_run_hitl` only fired for `UNVERIFIED`, so every gated call took the "log and proceed" branch and the HITL broker was unreachable — regardless of `NOVA_HITL_BROKER`. | A destructive capability now requires approval whatever the skill claims, asked through MCP elicitation (`mcp/approval.py`). Note `NOVA_HITL_BROKER=policy` no longer suppresses these; it covers only paths with no client to ask. |
| 9 | 2026-09-07 | `mcp/ONBOARDING.md` | The onboarding flow's first action failed on a fresh install. Its `nova_shard_create` example passed `user_message` and `ai_response`, neither of which is a field of `ShardCreateInput`, to a model that forbids extra fields. | Rewrote the example against the real schema. `tests/test_doc_examples.py` now parses it and validates it, so a documented call cannot drift from the schema again. |
